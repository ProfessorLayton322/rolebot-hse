# Agentic tool operating rules

- Yandex Cloud and YDB are frozen legacy targets. Commit `01aab7f35014c2b18b2c7ff489c3b3cbe76722f3` is the final Yandex-supporting baseline; preserve it in Git history as the reference for the last known-good Yandex state.
- Treat Yandex Cloud, YDB, and Yandex Disk as operationally unreliable legacy services. Upload every administrative roster, player-safe roster, and pass table to both Google Drive and Yandex Disk, and persist both URLs when available. Google Drive is the required and authoritative showcase destination: every such table must have a persisted Google Drive URL. Treat the Yandex Disk upload as best effort; if Yandex Disk errors, times out, or does not respond, treat it as unavailable for that operation, do not let it define readiness or block delivery, and rely on the Google Drive link.
- Do not develop, repair, deploy, migrate, or maintain feature parity for Yandex Cloud or YDB. Preserve the existing legacy implementation unless the user explicitly requests its removal.
- From the commit after that baseline onward, all cloud infrastructure and database development must target AWS and DynamoDB only.
- Keep the bot entirely within the AWS Free Tier/free quota. Never incur paid AWS usage or spend promotional credits. Before creating, resizing, or reconfiguring an AWS resource, verify that the resulting configuration remains free; if zero-cost operation cannot be guaranteed, stop and request explicit user direction instead of applying the change.
- If the user explicitly requests a future return to Yandex Cloud or YDB, derive the complete catch-up work from the preserved baseline and the then-current AWS/DynamoDB implementation, then implement the required migration as a new effort. Do not proactively keep Yandex ready in the meantime.
- Use `gh`, the AWS CLI, and pinned `wrangler` commands to inspect GitHub, AWS, and Cloudflare when relevant. For production AWS inspection, pass `--profile rolebot-bootstrap-advanced --region eu-central-1` explicitly and verify the active identity with `aws sts get-caller-identity` before relying on the results. Use `yc` only for read-only inspection of the frozen legacy state or for planning an explicitly requested return to Yandex.
- Push repository changes only to a non-default branch and deliver them through a pull request. Never push directly to `main`.
- Create exactly one pull request and start exactly one merge per user prompt. There is only one attempt: do not create corrective or follow-up pull requests for the same prompt.
- Use the repository's quiet `gh`-based PR script to create the pull request and start its merge. After the script starts the merge, end the prompt immediately without waiting for pull-request checks, merge completion, deployment, or smoke tests.
- Always run the project's pinned `ruff format --check .` before delivery. If it fails, format the affected files with the pinned Ruff version and rerun the check until it passes.
- Preserve unrelated working-tree changes and verify behavior in proportion to deployment risk before considering work complete.
- Every Telegram inline button's final `callback_data` must satisfy `1 <= len(callback_data.encode("utf-8")) <= 64`. This is a payload byte limit, not a button-label or character-count limit; one oversized callback can cause the entire reply to be rejected and appear as bot silence. When adding or changing buttons, verify the final encoded payloads for both inline replies and deferred sends using full production-sized IDs (including 36-character event UUIDs) and any supported non-ASCII data, not just short test IDs. Use compact, reversible callback encoding through `src/larp_bot/adapters/telegram/callbacks.py` where needed; never truncate identifiers. Cover the byte limit and callback decoding/routing in regression tests, preserving compatibility with previously sent buttons. See [Telegram's InlineKeyboardButton contract](https://core.telegram.org/bots/api#inlinekeyboardbutton).
- In user requests and user-visible text, "gamemaster" and "master" mean the role stored internally as an event `leader`, while "moderator" means the role stored internally as `gamemaster`. Preserve the existing internal names in code, configuration, and YDB.
- Treat "user" and "global user" as synonyms: both mean the person behind mutually linked Telegram and VK accounts when both profiles point to each other. "Local user" is distinct and means only the concrete Telegram profile talking to the Telegram bot or VK profile talking to the VK bot.
- Keep the Russian PDF administrator guide and its source ordered so the first substantive section is the quick end-to-end game lifecycle, followed immediately by Telegram chat setup and management. In that quick guide, keep chat creation, the bot's required administrator rights, and `/tie` in one step, followed by a separate step for sending the stored link to confirmed players.
